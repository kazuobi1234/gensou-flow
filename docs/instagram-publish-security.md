# Instagram公開連携：安全設計と事前確認（2026-10-19）

## 現状（接続済み環境で確認）
- Supabase `instagram-publish` v10 は `x-posting-secret` の一致だけで実行可能。リクエストの `publish: true` でMetaへの公開操作を実施する。
- `instagram-approval` v2 はFirebase IDトークンを検証するが、`preview` の入力形式チェック専用。公開不可。
- `instagram-image-upload` v2 はFirebase IDトークンを検証して画像URLを返す。
- Webアプリ `index.html` の `approval.status === "承認"` はブラウザから送られる状態であり、単独では公開権限の証拠にならない。
- Webアプリの `persist()` はFirestore保存完了をawaitせず、承認後のクラウド反映成功が保証されていない。

## 本番公開機能の前提条件（未実装）
1. 公開専用ゲートウェイはFirebase署名・issuer・audience・有効期限・許可UIDを**サーバー側で**確認する。
2. 公開ごとに本人の明示的な最終確認を要求する。UI上の「承認済み」だけでは公開しない。
3. ゲートウェイはFirestore等の**サーバー保持**の承認記録を読み取る。クライアントから送られる `approved: true` を信用しない。
4. 申請されたプロジェクトID、投稿本文、画像URL、承認した内容の一致を照合する。下書きを承認後に変更したら再承認が必要。
5. 投稿ごとの一意な要求IDを保存し、再送・二重タップ・タイムアウト時に重複公開しない。リトライはMeta側の結果照会後。
6. Metaアクセストークンと合言葉はサーバー環境変数のみに保持する。PWA/GitHub PagesのJavaScriptへ渡さない。
7. 既存の `instagram-publish` を直ちに公開UIへ直結しない。必要なら内部専用に変更・合言葉のローテーションも検討する。
8. 検証は「無認証は拒否」「別UIDは拒否」「承認なしは拒否」「入力不一致は拒否」「重複要求は拒否」「正当な申請でも公開直前まで止まる」を最低限含める。
9. 公開の有効化前にMeta権限・公開アカウント・画像の到達性・APIバージョンを確認する。

## 次の実装単位
- Phase A: 新しい公開ゲートウェイの認証と入力検証（常時 `published:false`、外部公開呼び出しなし）
- Phase B: サーバー側の承認記録と一意な投稿キーの保存・照合
- Phase C: 本人操作による公開確定と、実際のMeta送信・結果記録
- Phase D: 非公開テスト、権限テスト、重複テスト、明示的な本番試験

**この文書は安全設計であり、Instagramへの公開を有効にしたものではありません。**
